# Helper audit, 2026-10-21

Independent review (separate agent, no part in writing the code) of the helper extension before store submission.
No critical findings: a website can't use the helper to move funds, reach keys or sign anything without the user's
approval in the wallet; the only network call is the read-only `would_pay` on the configured station and node.

| # | Finding | Status |
|---|---|---|
| H1 | Passes are charged by a transaction's Mana *limit*; the helper raised missing limits to the 2 Mana maximum, so one action could use 2 Mana of a pass | **Fixed.** The helper keeps the site's own limit whenever the station could accept it (0.01 Mana up to the station's per-transaction maximum), so bigger transactions keep the room they need; it uses 0.5 Mana only when the site gave none, 0, or more than the maximum (usually a whole wallet balance). Kondor's "optimize mana" then sets ~1.1x real use. Counting by limit is stated in the terms. (0.3.1, after Carl's question about larger SwarmTales transactions.) |
| M1 | A wallet with 0 Mana had its limit carried over as 0; uploads capped at the station maximum would fail | **Fixed.** 0 or oversized limits are replaced by the default; uploads are left alone (they use tickets on the site). |
| M2 | A page could make the background run a 90 s decode or a huge allocation, or flood the node | **Fixed.** Strict checks (addresses, entry points, base64url args up to 64 KiB, 1 to 10 call operations, limit up to the maximum), address length cap in the encoder, one question at a time and 20 a minute per tab. |
| M3 | Ran on every kind of page; told every site the user has the helper; disclosures | **Partly fixed on 2026-10-21, corrected 2026-10-22** (Audit Bot AB-014 found the claim didn't hold: `bridge.js` still posted its on/off state to every page and answered any page's question). Now: https and localhost only (plus local files in the testnet build); the "helper is on" marker and the on/off state only on the Mana Station site; questions must carry a per-page-load secret shared by `page.js` and `bridge.js` before any site script runs; the `postMessage` wrapper reads as the native function to a casual check (not to a careful one: audit-2026-10 W1-02 below). **2026-10-22 (Audit Bot AB-026):** the question and answer no longer go through `window.postMessage` (where a signing page's own scripts saw them, secret included): they are DOM events whose type includes the per-load secret, sent with built-ins `page.js` saves before any site script runs, and the answer's `detail` is read with the saved native getter. Checked offline with the real unpacked extension in Chromium (the station became payer; the page saw no question, answer or secret). **2026-10-22 (Audit Bot AB-038):** that last claim didn't hold: page.js resolved a Promise with the parsed answer inside the answer event, so a site getter on `Object.prototype.then` ran during the event and read the secret from `window.event.type` (confirmed in Chromium). Now page.js uses no Promises, copies the request into objects and arrays with no prototype, reads only own data properties of an answer and hands plain values on in a later task, and calls no RegExp, string or number methods. Checked in node (test/page.audit-fixes-3.test.mjs: getters on Object/Array prototypes, replaced Promise, RegExp, String, Number, JSON, Object and Function built-ins) and in Chromium (test/chromium_secret_check.py, which also shows the old page.js leaking). Remaining: a site that tampers with built-ins can still notice that something on the page read its own signing request; it can't read the question, the answer or the secret, or answer for the extension. Manual check with the real extension: test/MANUAL_CHECKS.md. Privacy notice and store disclosures updated. **Deferred:** asking per site (optional host permissions), which adds friction. |
| L1 | A page can forge answers / inflate the counter | **Fixed:** answers must carry a plain number; the count comes only from the station's yes answers in the background. **2026-10-22 (Audit Bot AB-022):** an answer must also keep exactly the Mana limit that was asked about, so a forged answer can't raise it. |
| L2 | Checks and the forwarded copy could differ (getters), built-ins replaceable | **Fixed:** built-ins saved before site code runs; one private copy is checked and forwarded. Tested with a getter that swaps operations. |
| L3 | Wrapper differences from native postMessage | **Fixed:** requests it won't change go through at once, unchanged; `this` respected; errors reported back to the caller. |
| L4 | Switched off wasn't fully off | **Fixed:** the page part learns the setting and asks nothing while off. |
| L5 | Payer choices made elsewhere could be overridden | **Fixed** for send options (payer/payee/limit set by the site: left alone). Kondor's own "free mana" box is the user's choice in Kondor's window and still wins. |
| Q | Can someone spend another wallet's pass by naming it as payee? | **No.** Tested on the live testnet: the chain refuses ("account … has not authorized transaction") without the payee's signature. |
| AB-016 | (Audit Bot, 2026-10-22) A node that never answered locked the helper off on that tab | **Fixed:** node requests time out after 5 s (`AbortSignal.timeout`); each question gets 2.5 s in the background; a question that arrives while another is in flight waits for it and is asked only if that one timed out. |
| Info | Encoder correct; edge cases | Negative values and bad entry points refused; base64url only; leftover file removed. |

| **audit-2026-10** | Mainnet audit (2026-10-23, tag `audit-2026-10`), helper 0.4.0: | |
| W1-01 | A page that pre-set `data-ms-helper` could detect the helper, read the secret and forge answers | **Fixed.** No DOM attribute: `bridge.js` (isolated world) makes the secret and hands it to `page.js` (main world) with a synchronous event handshake at document_start, before any site script runs (`ms-hello-p` / `ms-hello-b`). Test: `test/page.audit-2026-10.test.mjs`. |
| W1-02 | The disguised `postMessage` is still detectable | **Accepted, stated.** A careful site can tell the wrapper from the native function. It still can't read the question, the answer or the secret, or answer for the helper. STORE.md and the privacy notice no longer say it can't be detected. |
| W1-08 | The helper keeps a site's Mana limit up to the station's maximum, so a hostile site can spend a user's daily pass | **Accepted (Carl, 0.3.1, H1 above).** Bigger SwarmTales-style transactions need their room. The pass's daily Mana caps the loss at one day of the pass; the terms say passes are counted by limit. The user still approves every transaction in the wallet. |
| W1-09 | `optsSend: {}` hid a payer chosen in `options` | **Fixed.** A payer, payee or limit in either object is left alone. |
| W1-10 | "Helper off" reached `page.js` only on Mana Station sites | **Fixed.** The setting reaches `page.js` on every site, on the private `ms-state-<secret>` event. |
| W1-11 | The real-Kondor path has never been run end to end | **Open, manual:** `test/MANUAL_CHECKS.md` on mainnet with a small pass, before the store listing (Kondor knows only mainnet and Harbinger). |

Open, by design: Kondor's window is where the user sees the payer (under Advanced); a short in-page notice before
Kondor opens is a possible later addition.

Tests: `test/test_helper.py` (page part), `test/test_background.mjs` (background and encoder), the `test/*.test.mjs`
regression files (node), `test/chromium_secret_check.py` (Chromium),
`test/live_test.py` (real unpacked extension on the Koinos testnet: station pays with the helper on, not with it off).
